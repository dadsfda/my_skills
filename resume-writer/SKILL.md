# AI App Engineer Resume Writer

基于“写作原则 + AI 应用项目亮点 + 用户画像 = 定制化简历”的三角模型，生成面向 AI 应用开发工程师岗位的高质量项目经历。

适用方向包括：AI 应用开发工程师、LLM Application Engineer、RAG Engineer、Agent Engineer、AI Backend Engineer、全栈 AI 工程师。

---

## 工作流程

### Phase 1：加载知识

优先读取以下文件：

1. `references/resume_principles.md`
   简历四段式结构、技术标签、亮点挖掘策略、常见误区。

2. `references/ai_app_project_highlights.md`
   AI 应用开发项目常见技术亮点、话术方向和量化角度。

3. 用户提供的项目文档、README、架构说明或源码
   用于补充真实模块细节，避免编造不存在的功能。

如果 reference 文件不存在，则使用本 skill 内置规则生成。

---

### Phase 2：用户画像采集

一次性收集最多 4 个问题。不要反复追问，除非用户给的信息无法写出可信简历。

#### 问题 1：目标岗位

让用户选择或填写目标方向：

- AI 应用开发工程师
- LLM Application Engineer
- RAG Engineer
- Agent Engineer
- AI Backend Engineer
- 全栈 AI 工程师
- 其他

该答案决定技术关键词策略和亮点筛选优先级。

#### 问题 2：业务背景

这是生成高质量“背景”段的关键输入，必须主动引导用户具体描述：

> 简历的“背景”段需要真实业务场景来打动面试官。请描述你的实际项目背景，越具体越好：你的团队或业务做什么？用户是谁？信息源是什么？现有流程有什么痛点？为什么需要 AI 应用？如果你不想绑定具体业务，也可以说明“通用 AI 应用框架”。

引导示例：

- “客服团队需要基于产品手册和历史工单快速回答客户问题，人工检索慢且口径不一致。”
- “研发团队的接口文档、故障记录和发布说明分散在多个系统，排查问题时需要跨平台搜索。”
- “法务团队需要从合同、法规和内部制度中快速定位条款，关键词搜索无法覆盖语义近义表达。”
- “运营团队需要批量生成、审核和改写营销内容，但人工流程慢，质量不稳定。”

如果用户选择“通用框架”模式，背景段聚焦“企业级 AI 应用底座 / RAG 框架 / Agent 平台”的技术叙事。

#### 问题 3：技术侧重

让用户多选或自由填写：

- LLM 调用链路
- Prompt 工程
- RAG / Hybrid Search
- Embedding / 向量数据库
- Rerank / 结果融合
- Agent / Tool Calling
- MCP 协议
- 多模型适配
- 异步任务 / 消息队列
- 可观测性 / 日志追踪
- 评估体系
- 权限 / 安全 / Prompt Injection 防护
- 成本优化
- 前后端流式输出
- 工程化 / 测试 / 部署

用户选择的技术侧重优先覆盖默认岗位排序。

#### 问题 4：特殊要求

让用户补充：

- 中英文版本
- 5 条 bullet 以内
- 偏后端 / 偏 Agent / 偏 RAG / 偏工程化
- 帮我补合理量化指标
- 更像真实业务项目
- 更适合校招 / 社招 / 实习 / 转岗
- 简历已有内容，需要优化而不是重写

---

### Phase 3：亮点匹配

根据目标岗位筛选 3-5 个亮点。

| 岗位方向 | 优先亮点 |
|---|---|
| AI 应用开发工程师 | LLM 调用链路 → RAG → Prompt 工程 → 后端 API → 评估与观测 |
| LLM Application Engineer | Prompt 工程 → 多模型适配 → Function Calling → 评估体系 → 成本优化 |
| RAG Engineer | 文档入库 → Chunking → Hybrid Search → Rerank → 检索评估 |
| Agent Engineer | Agent 状态管理 → Tool Calling → MCP → 错误恢复 → 工具权限 |
| AI Backend Engineer | API 设计 → 异步任务 → 缓存与队列 → 降级重试 → 部署观测 |
| 全栈 AI 工程师 | 流式交互 → 前后端联调 → RAG 问答 → 用户反馈 → 上线闭环 |

通用加分亮点：

- 可观测性：记录 prompt、retrieval context、token、latency、model、trace id。
- 评估闭环：离线评估集、人工标注、A/B 测试、用户反馈回流。
- 稳定性：超时、重试、限流、降级、兜底回答。
- 成本优化：缓存、模型分层、token 压缩、按场景选择模型。
- 安全治理：权限过滤、Prompt Injection 防护、敏感信息脱敏。

---

### Phase 4：四段式内容生成

严格生成四段：背景 → 目标 → 过程 → 结果。

#### 段 1：背景

必须基于用户在问题 2 中提供的真实业务背景撰写，不要套模板。

写法：

`在[团队/业务场景]中，[具体信息源/任务]分散于[系统/流程]，[服务对象]在[具体场景]下面临[痛点]，传统[搜索/人工/规则]方式难以满足[准确率/效率/一致性/规模化]要求。`

示例：

> 在企业客服场景中，产品手册、历史工单和 FAQ 分散在多个知识库，客服人员在处理复杂客户问题时需要跨系统检索，传统关键词搜索无法理解语义表达，导致响应慢、答案口径不一致。

通用框架写法：

> 针对企业 AI 应用落地中私有知识难接入、模型回答不可控、工具调用链路难观测等共性问题，设计并实现面向业务系统的 AI 应用开发框架。

#### 段 2：目标

说明技术目标和预期效果。

写法：

`为解决[核心问题]，目标构建[系统/平台/能力]，实现[关键技术能力]，并在[准确率/延迟/成本/效率/稳定性]上达到可量化提升。`

示例：

> 为提升客服知识检索和回答一致性，目标构建基于 RAG + LLM 的智能问答系统，实现私有知识语义检索、上下文增强生成和人工反馈闭环，将复杂问题平均处理时间降低 30% 以上。

#### 段 3：过程

生成 4-6 条 bullet。每条遵循：

`动词开头 + 做了什么 + 用了什么技术 + 达成什么效果`

要求：

- 每条不超过 80 字。
- 优先使用强动词：设计、实现、构建、优化、集成、主导、落地。
- 避免“参与”“负责”“了解”。
- 每条尽量包含一个技术关键词和一个可验证结果。
- 不堆工具名，必须说明工具的作用。

可用 bullet 模板：

- 设计 LLM 调用抽象层，封装模型路由、超时重试和流式输出，支持多模型平滑切换。
- 构建文档入库 Pipeline，完成清洗、切分、Embedding 和增量更新，支撑万级文档检索。
- 实现 Hybrid Search 检索链路，结合关键词召回、向量召回和 Rerank，提高复杂问题命中率。
- 集成 Function Calling / MCP 工具调用能力，使 Agent 可安全调用内部 API 和知识服务。
- 建立 LLM 可观测链路，记录 prompt、context、token、latency 和 trace id，提升问题定位效率。
- 优化 token 使用和缓存策略，通过 prompt 压缩、结果缓存和小模型分流降低调用成本。
- 设计离线评估集和人工反馈闭环，用 Hit Rate、Faithfulness、Answer Relevance 评估效果。
- 实现权限过滤和敏感信息脱敏，防止越权检索、Prompt Injection 和隐私泄露。

#### 段 4：结果

用 2-3 句总结项目成果，必须包含至少 3 个量化指标。

写法：

`系统上线后，[准确率/命中率]达到 X，[延迟]控制在 X，[规模]支撑 X，[成本/效率]提升 X。`

如果用户没有提供数字，给出“建议值，请根据实际调整”。

### Phase 5：量化指标策略

如用户提供具体数字，直接使用。

如用户未提供，基于项目能力给出合理建议值，并明确标注“建议值，请根据实际调整”。

| 指标类型 | 建议范围 | 适用场景 |
|---|---:|---|
| 检索命中率提升 | 15%-30% | RAG / Hybrid Search |
| 回答准确率 | 80%-92% | 知识问答、客服、内部助手 |
| 端到端延迟 | 800ms-3s | 非流式问答 |
| 首 token 延迟 | 300ms-1.5s | 流式输出 |
| 文档规模 | 1,000-50,000 篇 | 企业知识库 |
| Chunk 数量 | 10,000-500,000 | RAG 入库 |
| 日均查询量 | 1,000-100,000 次 | 业务系统集成 |
| 人工处理时间下降 | 20%-50% | 客服、运营、法务、研发知识检索 |
| Token 成本下降 | 15%-40% | 缓存、压缩、模型分层 |
| 线上问题定位时间下降 | 30%-60% | 可观测性建设 |
| 自动化测试覆盖 | 60%-85% | 工程化项目 |

禁止使用离谱指标，例如：

- “准确率 99%+”
- “延迟 50ms 内完成 LLM 回答”
- “单人支撑千万级并发”
- “完全消除幻觉”

### Phase 6：输出格式

严格按以下模板输出：

```text
**[项目名称]** | [时间段] | [角色]

**背景**：[2-3 句描述业务场景、服务对象、问题和需求]

**目标**：[1-2 句说明技术目标、核心能力和预期效果]

**过程**：
• [Bullet 1：核心架构 / LLM 调用链路]
• [Bullet 2：RAG / Agent / 工具调用]
• [Bullet 3：后端工程 / 异步任务 / 稳定性]
• [Bullet 4：评估 / 可观测性 / 安全]
• [Bullet 5：成本 / 性能 / 业务成果]

**结果**：[2-3 句汇总核心量化指标]

**技术栈**：[按岗位权重排列的关键词列表]
```

约束：

- 四段缺一不可。
- 过程段 4-6 条 bullet，除非用户指定。
- 每条 bullet 不超过 80 字。
- 结果段至少 3 个量化指标。
- 项目名称默认使用“智能知识检索与 AI 问答系统”，可根据业务背景调整。
- 如用户要求英文版，先给中文，再给英文，避免英文内容脱离中文事实。

---

### Phase 7：迭代与面试准备

输出初稿后，主动提供：

1. 可调整方向：更偏 RAG、Agent、后端、全栈、工程化、业务结果。
2. 面试追问预测 3-5 条。
3. 风险提示：哪些表述需要用户确认，哪些指标是建议值。

追问预测示例：

- 你的 RAG 链路中 chunk size 和 overlap 怎么选？
- Hybrid Search 的关键词召回和向量召回如何融合？
- Rerank 放在哪一步？失败时怎么降级？
- Function Calling 的 schema 怎么设计，参数校验在哪里做？
- 如何判断坏回答是检索问题、Prompt 问题还是模型能力问题？
- 线上日志记录哪些字段才能复盘一次错误回答？
- 你怎么控制 token 成本和模型超时？
- Prompt Injection 和权限越权怎么防？

## 放大策略

| 维度 | 允许 | 禁止 |
|---|---|---|
| 业务场景 | 包装成真实业务落地 | 编造公司名、客户名、产品名 |
| 量化指标 | 添加合理建议值并标注待确认 | 使用明显不可信的夸大指标 |
| 角色贡献 | 写“设计并实现”“主导核心模块” | 虚构团队规模和管理职责 |
| 技术深度 | 强调架构、取舍、评估、上线 | 编造未实现技术 |
| 项目规模 | 根据业务合理估算文档和查询量 | 脱离场景写百万/千万级规模 |

底线：

- 不声称使用了用户项目中不存在的技术。
- 不把 demo 写成大规模生产系统。
- 不写面试中无法自圆其说的指标。
- 对建议指标必须标注“建议值，请根据实际调整”。

---

## 反模式检查

输出前检查简历不包含：

- “负责大模型相关工作”这类泛化描述。
- “使用 LangChain、OpenAI、Redis、Docker”这类工具堆砌。
- 没有业务背景。
- 没有量化结果。
- 没有个人贡献边界。
- 过程段过长、没有主线。
- 声称“完全解决幻觉”“准确率 99%”等不可辩护表述。
- 写了 RAG / Agent / MCP，但无法解释实现链路。

---

## 输出语气

简历内容要专业、具体、可信。

默认使用中文输出。用户要求英文或中英双语时，再输出英文版。

不要把内容写成项目说明书。简历要强调：

- 做了什么
- 用了什么关键技术
- 解决了什么问题
- 带来了什么可量化结果
- 面试时是否能讲清楚
